**Change:**

PROBLEM: clw-snapshot's snapshot() (and build_manifest_local()) read each file entirely into RAM via tokio spawn_blocking + std::fs::read, then call chunk_bytes(&data), then RE-SLICE &data[offset..offset+len] to recover each chunk's raw bytes for upload. KEY EQUIVALENCE FACT (verified against fastcdc 3.2.1 source at v2020/mod.rs): FastCDC::new(&[u8], min, avg, max) and StreamCDC::new(R, min, avg, max) both call with_level(.., Normalization::Level1) with seed 0, share the identical GEAR table and identical cut-point algorithm, and differ ONLY in that StreamCDC pulls bytes from a Read into an internal buffer of capacity = max_size and yields ChunkData{hash,offset:u64,length:usize,data:Vec<u8>} (owning the bytes) instead of Chunk metadata over a borrowed slice. For the same byte sequence and same (min,avg,max) they MUST produce byte-identical chunk boundaries (offset+length) and therefore identical BLAKE3 digests. This is what the equivalence proptest locks down.

## M1.3 — Full Option A rate-limit client: honor Retry-After + AIMD adaptive global concurrency on 429

**Files:** /Users/gustavoschneiter/Documents/HuGR/corelink-workspaces/crates/clw-client/src/lib.rs, /Users/gustavoschneiter/Documents/HuGR/corelink-workspaces/crates/clw-client/Cargo.toml, /Users/gustavoschneiter/Documents/HuGR/corelink-workspaces/crates/clw-cli/src/main.rs, /Users/gustavoschneiter/Documents/HuGR/corelink-workspaces/crates/clw-cli/src/subcmds/snapshot.rs, /Users/gustavoschneiter/Documents/HuGR/corelink-workspaces/crates/clw-snapshot/src/lib.rs

**Size:** M  ·  **Model:** claude-opus-4-8[1m] (the AIMD/governor concurrency logic and the out-of-band Retry-After threading that must NOT touch the frozen contract are the kind of careful, invariant-sensitive async Rust work that warrants the strongest model; a lighter model risks deadlocking the semaphore or leaking the throttle hint through ClwError)

**Contract impact:** Touches the frozen contract ZERO times if done as specified. clw-types/src/lib.rs is the frozen wave-0 contract; this WP must NOT edit it. Specifically: do NOT add a `RateLimit`/`Throttled` variant to `ClwError`, do NOT change `ClwError::Http` (it has `status: u16, context: String` — sufficient; 429 already flows through it), and do NOT change the `CasTransport`/`AcTransport` trait signatures. The Retry-After hint is threaded out-of-band inside clw-client (a governor field/cell), never through the public error type or trait surface. The only public-API additions are NON-contract, additive, and live in clw-client (`HttpClient::with_concurrency`) and clw-snapshot (`SnapshotOptions::with_concurrency` / a settable field) — these are downstream crates, not the frozen seam, so no contract decision record is required. If a future iteration wanted to surface "we were throttled" to the user as a distinct error, THAT would be a frozen-contract change requiring a lead decision record — explicitly out of scope here.

**Change:**

Today the client (clw-client/src/lib.rs `with_retry`) does blind retry on 429: it sleeps a fixed schedule from `RETRY_SLEEP_MS = [200, 800, 2000, 5000, 10000]` for up to `MAX_ATTEMPTS = 6`, ignoring the server's `Retry-After` header, and there is no global throttle — every in-flight request (chunk uploads are fanned out at `buffer_unordered(concurrency)` in clw-snapshot) retries independently, so a throttled tenant keeps hammering at full concurrency. This WP upgrades it to full Option A: (1) honor `Retry-After`, and (2) AIMD-adaptive global concurrency that contracts on 429 and recovers on success.

PART A — clw-client/src/lib.rs (the core, ~all the substance):

1. Add a shared rate-limit governor to `HttpClient`. Add a private struct (e.g. `RateGovernor`) holding a `tokio::sync::Semaphore` (the global concurrency gate, wrapped in `Arc`) plus an `AtomicUsize` "current limit" (the AIMD target) and an `AtomicU64` "permits currently issued" counter so the effective concurrency can shrink/grow. Because `tokio::sync::Semaphore` cannot shrink below permits already handed out, model AIMD as: keep a `max_permits` semaphore created at construction sized to the configured ceiling, and a separate atomic `current_limit`. Before each network attempt, acquire ONE permit from the semaphore AND additionally gate on `current_limit` (the simplest correct realization: hold the semaphore at the *ceiling*, and implement AIMD by having the governor own an `AtomicUsize limit` plus a `Notify`; an acquire loop waits until `in_flight < limit`). Store the governor as `Arc<RateGovernor>` on `HttpClient` so it is shared across all clones/requests of one client instance — the throttle must be global per client, not per-call. Initialize `current_limit` to the configured concurrency ceiling (see Part B for how the ceiling arrives).

2. Wrap every network attempt inside `with_retry` so it first acquires a governor slot (RAII guard that decrements `in_flight` on drop). The acquire must respect the current AIMD limit, not just the static ceiling.

3. On a 429 response (detected inside the per-op closures where status is matched, OR — cleaner — surface the `Retry-After` value out of the op so `with_retry` sees it): apply AIMD multiplicative decrease — halve `current_limit` (floor at 1), i.e. `limit = max(1, limit / 2)`. On a fully successful attempt (op returned `Ok`): apply additive increase — `limit = min(ceiling, limit + 1)`. These updates are on the shared governor so all concurrent uploads converge.

4. Honor `Retry-After`. Parse the header from the 429 response: it is either an integer number of seconds (delta-seconds) or an HTTP-date. ## M4.2 — version/user-agent header on every CoreLink request

**Files:** /Users/gustavoschneiter/Documents/HuGR/corelink-workspaces/crates/clw-client/src/lib.rs

**Size:** S  ·  **Model:** Sonnet (claude-sonnet) — mechanical, single-file, well-scoped one-line behavioral change plus tests; no design judgment required

**Contract impact:** None. This does NOT touch the frozen clw-types contract. The `CasTransport`/`AcTransport` traits, their signatures, `Config`, `Digest`, and error types are all unchanged. The change is entirely internal to clw-client's reqwest client construction. No contract decision record is required (unlike M1.1/M1.2/M1.4 which the roadmap explicitly flags as frozen-trait changes — M4.2 is not in that set). The UA string is a new wire-level header but it is additive, header-only, and does not alter request/response bodies, paths, methods, or status handling.

**Change:**

Goal: every outbound CoreLink HTTP request (CAS GET/PUT/HEAD, AC GET/PUT — 7 total send sites) must carry a stable User-Agent of the exact shape `clw/<ver> (<os>; <arch>)`, e.g. `clw/0.1.0 (macos; aarch64)`.

Recommended single-point implementation (preferred, lowest-risk, covers ALL request types automatically including the existing HEAD and the GET-exists-fallback): set the User-Agent ONCE on the reqwest client builder inside `HttpClient::new` (lib.rs lines 50-57). reqwest's `ClientBuilder::user_agent(value)` installs a default `User-Agent` header on every request the client makes, so no per-call edits are needed and no request site can be missed.

Concrete change:
1. Add a module-level helper that produces the UA string. Source the version from `env!("CARGO_PKG_VERSION")` (compile-time; resolves to the workspace `version = "0.1.0"` — same pattern already used in clw-snapshot/src/lib.rs:267, so it is the established convention in this repo). Source OS from `std::env::consts::OS` and arch from `std::env::consts::ARCH`. Format exactly as `clw/{ver} ({os}; {arch})` — note the single space after `clw/<ver>`, parenthesized `os; arch` separated by `semicolon-space`, matching the roadmap M4.2 spec literally. Make this a small `fn user_agent() -> String` (or a `const`-built `&str` is not possible because consts::OS/ARCH are `&str` but version interpolation needs runtime format, so a function returning String, or a `once`/`LazyLock` static, is appropriate; a plain `fn` is simplest and called once at construction).
2. In `HttpClient::new`, add `.user_agent(user_agent())` to the `reqwest::Client::builder()` chain (between the existing `.timeout(...)` and `.build()`). Map any builder error through the existing `ClwError::Transport(e.to_string())` path already present.
3. Do NOT touch the per-call request builders; they inherit the default UA. Do NOT remove or alter the existing `Authorization` header logic.

Note on os/arch token spelling: `std::env::consts::OS` yields lowercase tokens like `macos`, `linux`, `windows`; `ARCH` yields `aarch64`, `x86_64`. These are exactly the tokens the roadmap example implies (`<os>; <arch>`). Document in a code comment that these are Rust's canonical target tokens (so server-side analytics has a stable enum), since they differ from `uname` spellings (e.g. `macos` not `Darwin`).

Why builder-level, not per-request: there are 7 send sites (exists HEAD at lib.rs:118, exists-fallback GET at :140, CAS get GET at :171, CAS put PUT at :223, AC get GET at :264, AC put PUT at :301 — and the verification requirement explicitly names CAS+AC GET/PUT/HEAD). Builder-level guarantees all are covered with one line and is immune to future new request sites being added without the header.

- clw run's memoization is keyed on inputs+command+env but NOT on toolchain identity in the SHIPPED code; the audit's M3 fix (tool-identity folded in, domain v1→v2) is UNMERGED (M0). A runner doing builds will get stale-replay across toolchain changes until M0 lands — the runner contract's correctness depends on M0 being merged first; call this out as a sequencing prerequisite.
- clw run streams full stdout/stderr only after the child exits (clw-run captures via wait_with_output) — for a long runner build this means no live log streaming; the runner owner may expect tee'd live output. Worth flagging as a known limitation in the contract.
- RefRecord concurrency is last-write-wins (single-operator assumption in clw-types). If multiple runners snapshot the same --name concurrently, refs silently clobber with no conflict detection — a real risk in a CI-runner fleet. Note as a contract limitation / future D-item.

RISK FLAGS found in cold review (NOT blockers for M0 merge — the audit closes real vulns and is net-positive — but log them as M1/M3 follow-ups so they are tracked, not silent):
1. clw-client loopback allowlist uses substring prefix matching: `http://localhost.evil.com` passes `starts_with("http://localhost")` and `http://127.0.0.1.evil.com` passes `starts_with("http://127.0.0.1")`. A crafted hostname can therefore exfiltrate the PAT over plaintext to a non-loopback host. The fix is to match the parsed host exactly (== localhost / 127.0.0.1 / ::1), not by prefix. 2. validate_symlink_target rejects empty/absolute/`..` but, unlike validate_rel_path, does NOT reject backslashes — a Windows symlink target like `..\\x` would slip the `..`-component check (it splits only on '/'). Tighten for the cross-platform release (M2.2).
3. resolve_tool_id reads the ENTIRE command[0] binary on every run-key compute (cargo/rustc can be tens of MB) — a real per-run cost on the hot path, and there is a TOCTOU window (the digested file is not provably the exec'd one) plus a silent `literal:` fallback when the tool isn't found, which weakens the staleness guarantee. Acceptable for correctness, worth a perf/robustness note in M1.
4. RUN_KEY_DOMAIN v1->v2 is a deliberate global memo-cache invalidation; it is documented in the CHANGELOG entry, so no action — just confirm release notes call it out so users expect a one-time cold cache.
